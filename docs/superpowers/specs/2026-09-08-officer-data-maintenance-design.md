# 航海士資料維護設計規格

## 目標

將現有「航海士資料投稿」擴充為可受控發布的資料維護流程。所有使用者都能提出新增航海士或修改既有航海士的工單；雲函數白名單管理員可審核並直接修正工單內容。只有已核准且成功通過本地同步、資料校驗、生成與小程序發布的工單，才會在正式名鑑生效。

航海士、技能、職業、語言、國家及其他關聯字典均採「可新增、可修改、不刪除」原則。

## 不變約束

- 資料三層架構維持 `archive/ → data/master/ → miniprogram/generated/`；`archive/` 唯讀，正式資料只由同步工具寫入 `data/master/`，不手改 `miniprogram/generated/`。
- 保持所有既有正式 ID。修改航海士不得更換 `officerId`；修改字典項不得更換其 ID。
- 新 ID 只能由受信任的同步流程依既有命名規則產生；使用者與小程序前端不可輸入、推測或產生正式 ID。
- 小程序運行時不直接寫入正式資料，也不新增 `wx.request`、`wx.cloud` 或遠端 URL。
- 所有正式資料變更通過 `npm run data:check`、`npm run data:generate` 與完整發布門禁後才可發布。

## 使用者流程

入口名稱為「資料維護」，提供兩項操作：

1. **新增航海士**：填寫新航海士資料後建立工單。
2. **修改既有航海士**：先搜尋正式名鑑並選取目標；表單載入目前資料，頁首固定顯示名稱、`officerId` 與基準版本，避免誤改。

提交者可保存草稿、提交待審核，並檢視自己的工單。已駁回工單可修正後重提，且每次重提建立新工單修訂，不覆蓋歷史內容。

## 關聯資料選擇與新增候選項

技能、職業、語言、國家使用統一的可搜尋實體選擇器：

1. 輸入關鍵字後，依正式名稱、別名與 ID 即時篩選。
2. 每筆結果顯示名稱、類型或分類及 ID，避免同名誤選。
3. 選取後以標籤顯示；技能與語言支援連續多選。
4. 搜尋無結果時，使用者可建立隸屬當前工單的候選項，不會立即寫入正式字典。
5. 候選項可在提交前修改或移除；提交時檢查必填、同類名稱重複、別名衝突與重複選取。

候選項最小資料如下：

| 類型 | 必填欄位 | 補充規則 |
| --- | --- | --- |
| 技能 | 名稱、技能分類 ID、說明、等級資訊（存在時） | 技能分類必須從既有可搜尋分類中選取；一般使用者不能新增分類。找不到適用分類時可填分類補充說明，交由管理員處理。 |
| 職業 | 名稱 | 可填別名。 |
| 語言 | 名稱 | 可填別名。 |
| 國家 | 名稱 | 可填別名與區域。 |

城市、招募條件等後續關聯資料可沿用此選擇器與候選項機制，不另建互動模式。

## 管理員審核與修訂

白名單管理員可載入待審核工單，檢視基準資料、提交內容與欄位級差異。管理員可直接修正航海士欄位、關聯選取、技能分類與候選項內容，也可將候選項合併到既有正式 ID。

每次管理員保存都建立不可變的審核修訂紀錄，至少保存修改者、時間、修改原因、提交者原始內容與審核後內容。管理員核准的是最後保存的審核版本；小錯誤應優先由管理員修正，不需要駁回。駁回只用於資料無法確認、缺少必要證據、重複航海士或需要提交者補充來源的情況。

若修改工單的基準版本已落後目前正式資料，系統標記衝突，禁止直接核准。管理員必須以最新正式資料重新比對並保存，或要求提交者重提。

## 工單模型與狀態

新增獨立的資料維護工單模型；現有 `custom_officers` 投稿模型不直接承擔正式航海士修改，避免混淆自訂航海士與正式資料。

每份工單至少包含：

- `workOrderId`：工單穩定 ID。
- `operation`：`createOfficer` 或 `updateOfficer`。
- `targetOfficerId`：修改工單必填，且建立後不可變。
- `baseDataVersion` 與基準快照：用於衝突檢查與差異檢視。
- `proposedData`：使用者提交內容。
- `reviewedData`：管理員最後保存且準備發布的內容。
- `referenceCandidates`：尚未入庫的二級資料候選項。
- `status`：`draft`、`pendingReview`、`approvedPendingPublish`、`published`、`rejected`。
- `history`：草稿保存、提交、管理員保存、核准、駁回、同步與發布的不可變紀錄。

狀態流轉：

```text
draft → pendingReview → approvedPendingPublish → published
                    └→ rejected → pendingReview（新修訂）
```

## 發布與資料完整性

核准不直接改動正式名鑑。同步工具只讀取 `approvedPendingPublish` 工單，按以下順序處理：

1. 重新驗證工單、正式 ID 與候選項名稱衝突。
2. 為核准候選項產生符合現有規則的新 ID，或解析為管理員指定的既有 ID。
3. 以 ID 為基礎更新 `data/master/skills.json`、`data/master/dictionaries.json` 與 `data/master/officers.json`；修改既有資料時保留原 ID。
4. 執行資料校驗、資料生成、資產流程與完整驗證。
5. 正式小程序發布成功後，將對應工單標記為 `published`，並記錄資料集版本。

任何一步失敗均不可標記已發布，工單維持待發布狀態供修正與重試。

## 驗證責任

| 層級 | 驗證內容 |
| --- | --- |
| 小程序 | 必填欄位、數值範圍、重複技能／語言、候選項名稱格式與即時搜尋結果。 |
| 雲函數 | 使用者與管理員權限、狀態轉換、引用 ID 存在性、候選項合法性、版本衝突與不可變歷史。 |
| 同步工具 | ID 產生與解析、schema、資料引用完整性、名稱衝突、`data:check`、生成檢查與發布狀態回寫。 |

## 實作分期

1. 建立工單契約、雲函數權限與狀態機，加入單元測試。
2. 實作統一可搜尋選擇器及候選項表單，先覆蓋技能、職業、語言與國家。
3. 實作新增／修改航海士工作區、草稿與工單列表。
4. 實作管理員差異檢視、工單修訂、候選項合併與核准／駁回。
5. 擴充同步工具，將已核准工單轉換為 `data/master` 變更；完成資料、生成與發布鏈路驗證。

每一期皆遵循 TDD，且不混入與資料維護無關的重構。
