# Uncharted Waters Origin 航海士资料查询小程序设计规格

日期：2026-07-28
状态：已完成讨论，待用户复核

## 1. 项目目标

第一版建设一个面向《Uncharted Waters Origin》国际服玩家的繁体中文微信小程序，用于查询游戏内全部航海士资料。

核心能力包括：

- 按名称查询航海士。
- 按稀有度、航海类型、职业、性别、语言、主动技能和被动技能筛选。
- 支持多条件组合筛选。
- 通过技能反查拥有该技能的航海士。
- 查看航海士完整资料、头像以及技能图标。

首批用户主要位于中国大陆和台湾。

## 2. 第一版范围

### 2.1 包含

- 全部航海士的基础资料。
- 稀有度、职业、性别、语言等分类资料。
- 主动技能、被动技能及技能图标。
- 名称搜索和多条件组合筛选。
- 航海士列表与详情数据。
- 完全本地化的数据和素材。

### 2.2 不包含

- 队伍配置、编队推荐或数值计算。
- 登录、账号体系和用户云数据。
- 收藏、持有状态或个人标记。
- 在线后台管理系统。
- 自动同步 voyage.tw。
- 服务器、数据库或付费云存储。
- 本地资料管理页面。该功能列入后续版本，但本期需为其预留统一的数据读写和校验边界。

## 3. 核心约束

- 使用原生微信小程序和 TypeScript。
- 界面及正式资料仅支持繁体中文。
- 第一版基础数据经授权后从 voyage.tw 一次性导入。
- 后续更新由项目维护者人工维护，不再依赖 voyage.tw。
- 所有文字、头像和技能图标随小程序本地发布。
- 上线后不得产生服务器、云数据库、云存储或图片流量费用。
- 为满足本地包体要求，可以只保留适合手机显示的图片清晰度，不保留小程序内的高清原图。
- 项目先使用本地 Git，不建立远程仓库。

## 4. 总体架构

数据采用三层架构：

```text
一次性网站导入 ─┐
               ├→ 统一主资料库 → 校验与构建 → 小程序运行数据
未来本地管理页 ─┘

原始网站快照仅用于留档、核对和重新导入。
```

三层职责如下：

1. 原始档案层：保存 voyage.tw 的一次性原始快照，内容不可修改，不进入小程序包。
2. 主资料库层：长期维护的唯一权威数据源，未来所有资料变更均在此进行。
3. 运行数据层：由构建工具自动生成，供小程序读取，不允许人工修改。

## 5. 目录职责

计划采用以下职责划分；实施阶段可在不改变边界的前提下调整具体名称：

```text
archive/
└─ voyage-tw-<snapshot-date>/
   ├─ raw-data/
   ├─ raw-assets/
   └─ source-manifest.json

data/
├─ master/
│  ├─ dataset.json
│  ├─ officers.json
│  ├─ skills.json
│  ├─ dictionaries.json
│  └─ assets.json
└─ schema/

tools/
├─ import/
├─ data-pipeline/
└─ asset-pipeline/

miniprogram/
├─ generated/
│  ├─ catalog/
│  ├─ indexes/
│  ├─ details/
│  └─ asset-manifest/
└─ assets/
```

现有微信开发者工具生成在项目根目录的 JavaScript 模板只作为初始脚手架。实施阶段将把小程序源码迁移到 `miniprogram/`，并在 `project.config.json` 中明确设置 `miniprogramRoot`；根目录只保留工程配置、原始档案、主资料、导入工具、测试和文档。迁移必须单独验证，避免旧根目录源码与新 TypeScript 源码并存。

### 5.1 原始档案

原始档案保存：

- 原始文字资料。
- 原始头像和技能图标。
- 抓取日期和来源网址。
- 已确认的授权/来源说明。
- 原文件哈希值。
- 导入器版本。
- 导入异常和字段映射报告。

原始档案不是未来维护对象。其作用是保留证据、核对导入错误以及在必要时重新运行导入流程。

### 5.2 统一主资料库

`data/master` 是唯一允许人工维护的正式资料库。所有航海士统一保存在 `officers.json`，技能统一保存在 `skills.json`，公共枚举和分类统一保存在 `dictionaries.json`。

未来本地管理页面也只能通过主资料库服务和校验模块读写这一层，不得直接修改小程序生成数据。

### 5.3 小程序运行数据

`miniprogram/generated` 完全由构建工具生成。任何人工修改都会在下一次构建时被覆盖。

## 6. 领域模型

### 6.1 稳定标识

- 每个航海士、技能、职业、语言和素材都拥有项目内部稳定 ID。
- 内部 ID 创建后不得因名称、职业、稀有度或来源字段变化而改变。
- 不使用繁中名称作为实体关联键。
- voyage.tw 的 ID 仅保存于 `sourceRefs`，不作为项目内部关系的唯一依据。

### 6.2 航海士

航海士记录至少包含：

- 稳定 ID。
- 繁中名称。
- 隐藏搜索别名。
- 稀有度 ID。
- 航海类型 ID；航海类型与职业是两个独立概念。
- 性别 ID。
- 职业 ID。
- 国籍 ID。
- 语言及熟练度列表。
- 技能引用列表及其关系属性。
- 招募城市、条件和前置航海士。
- 头像素材 ID。
- 稳定显示顺序。
- 来源引用。
- 可选备注和维护信息。

规范模型必须保存来源中所有具有业务意义的字段，即使第一版界面暂时不展示，也不得在导入时静默舍弃。

示意结构：

```json
{
  "id": "officer_000123",
  "name": "航海士名稱",
  "aliases": [],
  "rarityId": "rarity_5",
  "typeId": "type_combat",
  "genderId": "gender_female",
  "jobId": "job_xxx",
  "nationalityId": "nation_xxx",
  "languages": [
    {
      "languageId": "language_xxx",
      "level": 5
    }
  ],
  "skills": [
    {
      "skillId": "skill_0001",
      "kind": "active",
      "sourceGroup": "sk2",
      "unlockLevel": 1,
      "level": 1
    }
  ],
  "recruitment": {
    "cityIds": [],
    "requirementId": null,
    "requiredOfficerIds": [],
    "note": null
  },
  "portraitId": "portrait_000123",
  "displayOrder": 1,
  "sourceRefs": {
    "voyageTw": "source-id"
  }
}
```

### 6.3 技能

技能作为独立实体维护，至少包含：

- 稳定 ID。
- 繁中名称。
- 技能分类。
- 繁中说明。
- 图标素材 ID。
- 来源引用。

技能与航海士的关系是主动/被动属性的唯一真相源，并同时携带来源分组、槽位、解锁等级和技能等级等属性。技能实体本身不重复保存主动/被动；如果同一技能在不同关系中出现冲突属性，校验器必须将其列为异常。

来源站的 `sk0` 至 `sk5` 和技能分类不能凭名称猜测为主动或被动。导入器必须使用一份显式、可审计的映射表，将“来源分组/分类”映射到关系的 `kind` 与技能的 `categoryId`；任何未映射或有歧义的技能都必须令导入失败，并进入人工复核报告。

### 6.4 字典

稀有度、航海类型、职业、性别、国籍、语言、城市、技能分类以及其他固定分类都通过稳定 ID 维护。每个字典项具有明确的 `displayOrder`；稀有度另有独立 `sortWeight`。显示名称和顺序可以调整，但不会破坏航海士引用。

### 6.5 素材

素材清单负责记录：

- 稳定素材 ID。
- 所属实体。
- 原始文件信息。
- 小程序文件路径。
- 文件哈希。
- 宽高和格式。
- 处理规则版本。
- 所属素材分片。

## 7. 数据导入与后续维护

### 7.1 首次导入

首次导入流程：

1. 获取 voyage.tw 的文字和素材快照。
2. 保存来源、授权说明、导入器版本和文件哈希。
3. 解析原始字段并合并站点语言映射。
4. 建立项目内部稳定 ID。
5. 使用已审核的来源技能分组映射主动/被动及技能分类。
6. 去重技能和素材。
7. 输出主资料库候选数据。
8. 执行完整校验。
9. 生成字段映射、差异、异常和全量记录去向报告。
10. 人工确认每条来源记录已导入或有明确拒绝原因后，纳入主资料库。

导入工具是一次性数据接入工具，不会成为小程序运行依赖。

### 7.2 后续人工维护

后续修改只针对 `data/master`：

1. 修改或新增航海士、技能和素材。
2. 运行资料校验。
3. 重新生成查询索引、详情分片和素材清单。
4. 运行测试及包体检查。
5. 在微信开发者工具和实机中验证。
6. 提交本地 Git。

未来本地管理页面将复用同一套读写、校验和构建接口，并提供表单、关联选择、素材预览及保存前校验。

## 8. 查询与筛选

### 8.1 运行时投影

构建工具生成四类运行数据：

- `catalog`：列表所需的轻量航海士摘要。
- `indexes`：名称、稀有度、航海类型、职业、性别、语言和技能的倒排索引。
- `details`：完整航海士详情，按稳定 ID 分片。
- `asset-manifest`：实体 ID 到本地素材路径和素材分片的映射。

小程序启动时只加载轻量目录和索引，进入详情页时再读取对应详情分片。

### 8.2 组合规则

- 不同筛选类别之间采用“并且”关系。
- 稀有度、航海类型、职业、性别等单值类别内部多选采用“任一”关系。
- 语言和技能内部多选采用“全部拥有”关系。
- 名称搜索与其他筛选条件共同生效。
- 技能索引支持通过主动或被动技能反查航海士。
- 清除某一条件后仅重新计算结果，不重新读取全部数据。
- 默认排序固定为稀有度字典的 `sortWeight` 降序、航海士 `displayOrder` 升序、稳定 ID 升序；第一版不提供排序设置。
- 筛选条件只在本次名册浏览会话内保留，不跨小程序重启持久化。

627 名左右航海士不需要本地数据库或全文搜索引擎。使用紧凑倒排索引和 ID 集合交集即可获得稳定性能。

### 8.3 搜索语言

- 正式展示内容和第一版搜索词只使用繁体中文。
- `aliases` 仅保存经过人工确认的繁中简称、别称或异体字。
- 第一版不做自动简繁转换，也不自动生成简体搜索别名；未来需要时作为独立数据迁移增加。

## 9. 本地素材和分包

### 9.1 素材处理

- 原始图片保存在档案层，不进入小程序包。
- 默认只生成一种适合手机显示的尺寸，列表和详情尽量复用。
- 只有分包实验确认主包页面不能读取素材分片时，才允许额外生成超小型名册头像或图集；该变体仍须由同一素材流水线生成和校验。
- 文件使用稳定 ID 命名，不使用显示名称。
- 自动裁切、缩放、去重和压缩。
- WebP 与优化 PNG 必须经过 Android、iOS 和目标基础库实机验证后确定，不提前写死格式。
- 构建结果记录图片尺寸、格式、哈希和处理规则版本。

### 9.2 分包策略

素材按稳定 ID 分片，不能按职业、稀有度等未来可能变化的属性分片，以避免一次资料调整导致大量文件移动。

正式实现前必须完成一个最小技术实验：

1. 主包搜索页面调用 `wx.loadSubpackage`。
2. 加载指定素材分片。
3. 验证主包页面能否稳定显示该分包中的本地图片。
4. 在开发者工具、Android 和 iOS 上验证。

实验结果决定实现路径：

- 若支持：搜索结果出现时按需加载头像与技能图标分片。
- 若不支持：为名册生成经过强压缩的超小型本地头像或图集，详情继续从素材分片读取较大版本。
- 若仍超出预算：继续调整图片尺寸、质量、图集和分片边界，并重新实机验证；不得把所有名册头像静默降级为占位图。

名册中的小头像及其左上角稀有度图标是第一版必需体验。只有单个素材确实缺失或损坏时才使用占位图。无论实验结果如何，第一版都不引入远程图片源。

### 9.3 包体预算

构建阶段必须生成包体报告，并设置低于平台硬限制的内部安全预算。以下情况阻止发布：

- 单个分片超出预算。
- 总素材超过预算。
- 出现未分配素材。
- 出现缺失、重复或无法解码的图片。

## 10. 版本与可追溯性

主资料库的 `dataset.json` 至少记录：

- `schemaVersion`：资料结构版本。
- `contentVersion`：内容版本。
- `updatedAt`：资料更新时间。
- `sourceSnapshot`：首次来源快照标识。
- 航海士、技能和素材数量。

构建产物记录输入数据哈希和构建规则版本。相同输入和相同工具版本必须产生相同结果。

本地 Git 负责：

- 保存资料修改历史。
- 比较更新前后的差异。
- 回退错误修改。
- 将资料版本与小程序代码版本对应起来。

## 11. 错误处理

- 解析失败不得静默丢弃记录，必须输出异常报告。
- 未知枚举值不得自动映射到相似名称，必须进入待确认列表。
- 缺失引用、重复 ID、缺失素材和非法技能类型均视为构建错误。
- 非必填内容可以产生警告，但必须被记录。
- 小程序遇到单条详情异常时显示可理解的资料错误状态，不能导致整个列表不可用。
- 素材加载失败时显示统一占位图。

## 12. 开发规范与测试

工程使用：

- 原生微信小程序。
- TypeScript。
- ESLint。
- Prettier。
- 自动化测试。
- 本地 Git。

### 12.1 TDD

所有可独立验证的逻辑遵循：

```text
失败测试 → 最小实现 → 测试通过 → 重构 → 完整验证 → Git 提交
```

优先采用 TDD 的范围：

- 网站数据解析。
- 数据标准化。
- Schema 和关联校验。
- 名称搜索及组合筛选。
- 索引与分片生成。
- 素材命名、去重和预算检查。
- 数据版本和确定性构建。

### 12.2 测试分层

- 单元测试：纯 TypeScript 数据和业务逻辑。
- 数据契约测试：主资料库全部记录及引用关系。
- 构建快照测试：验证确定性输出。
- 组件测试：搜索框、筛选器、列表和详情组件。
- 自动化流程测试：通过微信开发者工具验证核心查询路径。
- 实机验证：至少覆盖 Android 和 iOS。

### 12.3 本地质量命令

计划提供：

```text
npm run lint
npm run format:check
npm run typecheck
npm test
npm run data:check
npm run build:check
```

在建立远程仓库前，这些检查全部在本地执行。未来如接入 GitHub，再增加 CI。

## 13. 实施前技术验证

正式页面开发前必须完成：

1. voyage.tw 全量记录和素材数量审计。
2. 原始字段到领域模型的完整映射及样本。
3. `sk0` 至 `sk5`、技能分类与主动/被动的映射审计，确认没有未决技能。
4. WebP 与优化 PNG 的质量、体积和兼容性比较。
5. 分包素材按需加载实验，并证明紧凑名册可保留头像和稀有度叠图。
6. Android 和 iOS 的本地图片实机验证。
7. 小程序生成数据的体积和解析性能测量。

只有这些验证通过后，才能确定最终图片尺寸、格式、分片数量和包体预算。

## 14. 已确认的设计决策

- 第一版只做航海士资料查询，不做队伍配置。
- 只提供繁体中文正式内容。
- 第一版按名称、稀有度、航海类型、职业、性别、语言、主动技能和被动技能查询或筛选，并支持组合条件；其他资料在详情中展示。
- 不把筛选、滚动位置等浏览状态持久化到下一次小程序启动；当前浏览会话内按交互规则暂存。
- 数据从 voyage.tw 一次性导入，之后人工维护。
- 采用原始档案、统一主资料库、运行数据三层架构。
- 主资料库按航海士、技能、字典和素材表统一管理。
- 后续通过本地管理页面维护，但第一版暂不实现。
- 文字和素材全部本地化。
- 接受压缩图片，不保留小程序内高清图。
- 零服务器和零运行费用是硬约束；名册小头像和稀有度叠图也是第一版必需体验，必须通过压缩、图集或分包同时满足。
- 业务逻辑和数据工具采用 TDD。

## 15. 成功标准

第一版完成时应满足：

- 每条来源航海士、技能和素材都已成功导入，或有经过人工确认的拒绝原因。
- 所有具有业务意义的来源字段和关联均被规范模型保存。
- 主动/被动及技能分类映射已经审核，没有未决技能。
- 全部已导入航海士均可查询，且默认排序结果稳定、可重复。
- 多条件筛选结果符合既定规则。
- 名册除单个缺失素材外均显示小头像、原始稀有度叠图和技能图标。
- 业务数据和素材均来自小程序包，不使用远程图片 URL、`wx.request`、自建服务器或付费云服务；微信自身按需下载分包不属于项目后端依赖。
- 数据可以通过统一主资料库持续维护。
- 数据和素材构建过程可重复、可校验、可追溯。
- 项目在 Android、iOS 和微信开发者工具中通过核心流程验证。

## 16. UI/UX 已确认设计

### 16.1 视觉语言

- 参考项目根目录中的两张游戏实际截图。
- 主色采用暖灰羊皮纸、炭黑、低饱和酒红、黄铜金和灰橄榄。
- 视觉方向为古典航海资料馆，不使用高饱和现代卡片风。
- 首版先确定信息结构；航海背景插画、罗盘、船帆、海图纹理和其他装饰元素后续深化。
- 所有正式界面文字使用繁体中文。

### 16.2 首页

首页采用 A「模块港口」方案：

- 顶部为应用名称和航海主题标识。
- 首版只显示已经上线的“航海士名鉴”主功能入口。
- 显示资料收录状态、数据版本和最近更新说明。
- 首页不提供航海士快速搜索框。
- 第一版不设置固定底部 Tab Bar。
- 未完成的未来功能不得提前显示。
- 新功能完成后，以模块卡片形式自然加入首页，不破坏现有结构。

### 16.3 航海士名册

名册采用技能优先的连续紧凑资料表：

- 不使用相互分离的大卡片。
- 每行保留小型航海士头像。
- voyage.tw 的原始稀有度素材叠放在头像左上角。
- 姓名下方显示职业和性别摘要。
- 主动技能和被动技能分别使用固定主列，并按稳定槽位顺序显示紧凑的本地技能图标组。
- 名册不得静默省略技能；若源数据的技能数量超过既定槽位，数据校验必须阻止发布并要求重新设计行布局。
- 语言可参与筛选，但不占用名册核心列。
- 每行目标高度约 47px，单屏目标显示约 11 名航海士。
- 点击头像、姓名或资料行空白区域进入航海士详情。
- 点击技能图标直接打开技能底部信息层。

### 16.4 四页式组合筛选

筛选结构参考 voyage.tw，拆分为四个独立页面：

1. 航海士：名称、稀有度、航海类型和性别。
2. 技能：技能名称搜索、折叠分类及主动/被动切换。
3. 语言：独立搜索和多选列表。
4. 职业：独立搜索和多选列表。

交互规则：

- 四个页面通过顶部页签切换。
- 进入筛选时复制当前已应用条件为草稿；页面切换保留草稿。
- “取消”丢弃本次草稿并恢复进入筛选前的条件；“应用”提交全部草稿并返回紧凑名册。
- 多个页面的条件可以累计并共同计算结果。
- 已应用条件只在本次名册浏览会话内保留，不跨小程序重启持久化。
- 稀有度使用原始素材图片，不使用 S、A、B 等替代文字。
- 技能页优先展示技能图标，并支持名称搜索。
- 底部实时显示当前草稿条件对应的航海士数量。

筛选逻辑继续遵守：

- 不同筛选类别之间采用“并且”。
- 稀有度、航海类型、职业、性别等单值类别内部多选采用“任一”。
- 语言和技能内部多选采用“全部拥有”。

### 16.5 航海士详情

详情页采用 A「技能优先卷宗」方案：

- 顶部紧凑显示头像、稀有度、名称、职业、性别和语言。
- 主动技能与被动技能紧接人物摘要显示。
- 技能图标旁显示技能名称。
- 其他资料放在技能区块之后。
- 所有资料在同一纵向滚动页面中，不依赖分页切换。

### 16.6 技能快速信息

点击技能图标后采用 A「底部快速信息」：

- 不离开当前名册或航海士详情页面。
- 显示技能图标、名称、主动/被动属性、技能分类和完整说明。
- 提供“查看拥有此技能的航海士”入口。
- 点击反查入口时建立只包含该技能的新筛选上下文并返回名册，以确保展示所有拥有者。
- 用户返回上一页时恢复反查前的名册筛选条件和滚动位置。

### 16.7 空状态与降级

- 没有符合条件的航海士时保留当前条件，并显示“清除全部筛选”按钮。
- 图片缺失或无法解码时显示统一航海主题占位图。
- 单个素材失败不能影响文字资料查询。
- 单条详情异常不能导致整个名册不可用。
