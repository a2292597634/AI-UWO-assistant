# 大流行微信提醒設計草案

狀態：用戶已確認最終 Demo 並指示繼續實作。實作於隔離分支 `codex/phase-62-major-event-reminders` 進行；本次不部署、不提交或推送。訂閱消息模板仍待配置。

## 1. 已確認需求

- 用戶在對應的某一次大流行選擇微信提醒；一場由海域、流行類型、精確開始時間共同識別。
- 完整觀看一次激勵視頻廣告，對應該場大流行的訂閱，不按提醒條數重複要求看廣告。
- 提醒時間固定為開始前 3 小時、1 小時、10 分鐘，各發送一次。
- 訂閱入口直接設在列表每次大流行條目內，採用簡單的膠囊形開關，唯一可見標籤為「提醒訂閱」；配色遵循小程序 Design Foundation。用戶無需先打開單次大流行詳情。
- 小程序介面、通知內容與文件使用繁體中文。

## 2. 微信能力核對與方案選擇

2026-10-29 已閱讀微信官方文件：

- [訂閱消息概述](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message-overview.html)：普通一次性訂閱每次授權僅允許下發一條對應消息；不能假設本工具有長期訂閱資格。
- [wx.requestSubscribeMessage](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/subscribe-message/wx.requestSubscribeMessage.html)：需由用戶點擊觸發，同次請求中模板標題相同會被過濾；成功回調仍須逐一檢查模板結果是否為 accept。
- [新版一次性訂閱 Beta](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message-2.html)：限定業態、模板與類目，不能假設本遊戲資料工具可透過 liveActivity 取得多次通知能力。
- [激勵視頻廣告](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/ad/rewarded-video-ad.html)：廣告由用戶主動觸發；按 onClose 的 isEnded 判斷完整觀看，頁面卸載時清理監聽。
- [發送訂閱消息](https://developers.weixin.qq.com/miniprogram/dev/server/API/mp-message-management/subscribe-message/api_sendmessage.html)：由服務端發送，支持雲調用 subscribeMessage.send，並有參數長度與錯誤碼約束。

可選方案：

| 方案 | 操作與條件 | 評估 |
| --- | --- | --- |
| A：同一模板，分次主動授權 | 三個未來提醒時點各點擊一次授權，再看一次廣告 | 推薦首版；不依賴取得三個不同標題模板 |
| B：三個不同標題模板 | 後台有三個符合類目、用途且標題不同的模板，才可嘗試一個彈窗請求三項授權 | 可能減少操作，須先核對真實模板，不能僅複製相同模板 ID |
| C：長期訂閱或新版服務動態 | 須符合微信指定業態與類目 | 不作為本功能基礎 |

以下設計採 A。微信的發送權限與看廣告是兩個獨立條件，不顯示「看完廣告自動取得微信授權」。拒絕任一授權不妨礙繼續查詢大流行。

## 3. 建議的產品行為

以下邊界為本草案的建議值，隨本設計一併確認：

- 在「日程」與「按流行」列表每個具體場次的條目內直接加入簡潔開關，標籤固定為「提醒訂閱」；不增加提醒圖示、狀態標題或副文案。使用既有海洋／黃銅色彩 Token，操作熱區至少 88rpx。
- 「按流行」條目採緊湊的左右各兩行：左側第一行為海域徽記＋海域名稱、第二行為「提醒訂閱」＋開關；右側第一行為日期＋開始時間、第二行為倒數。移除「最近一場」，保留詳情箭頭，控制兩側行間距與上下內距；窄屏仍維持兩行資訊結構，開關觸控高度至少 88rpx。
- 用戶要求進一步提高可讀性並縮小字與邊框間距：Demo 中海域名稱採 16px、開始時間 19px，日期、倒數與開關標籤採 14px；最窄版面相應為 14px、17px、13px。條目上下內距縮至 4px、左右 6px，保留 44px 的開關觸控高度。正式 WXML／WXSS 依 Design Foundation 對應字體層級與間距 Token 實作。
- 「日程列表」將簡潔開關放在事件標題區右側，原分鐘提示留在事件名稱旁，海域徽記與海域名稱保留在左側下方；交易品類標籤使用整行寬度自然換行。開關不能遮擋時間線、分鐘提示、品類圖示或文字。
- 用戶另確認：從日程列表打開具體流行詳情時，詳情內也提供「提醒訂閱」開關，放在發生時刻、海域與交易品類之後。詳情與兩種列表均按同一場次鍵讀寫訂閱狀態，開通、取消和恢復均同步反映，不能重複建立另一份訂閱。
- 點擊列表開關直接進入該場授權與廣告流程；流程可使用獨立操作浮層，不要求先打開大流行詳情。開關事件須阻止冒泡，避免誤觸列表原有的詳情入口。
- 正式功能需在服務端確認建立提醒後才顯示為已開啟；辦理或確認結果期間鎖定開關，使用進度指示與無障礙描述反映處理狀態，標籤仍固定為「提醒訂閱」。取消流程、拒絕全部授權或廣告未完成時維持關閉，保留可恢復的流程狀態。
- 部分授權的實際覆蓋在訂閱操作浮層與結果提示中明確告知。開關代表至少有一項有效待發提醒，不能透過成功提示暗示三次均已開通；列表開關旁仍只保留「提醒訂閱」。
- 關閉開關時確認取消該場尚未發送的提醒；服務端確認取消成功才顯示為關閉，失敗或結果不明時保留原狀並提示。所有提醒已發送、取消或過期後，顯示對應終態，不繼續顯示為有效開啟。
- 列表保留既有海域、類型與東八區日期時刻；三個提醒時點各自的狀態放在訂閱操作浮層。
- 用戶依次點擊「授權 3 小時前提醒」「授權 1 小時前提醒」「授權 10 分鐘前提醒」；每個按鈕的原生點擊直接觸發微信接口，不在廣告關閉或非同步雲請求之後自動喚起。
- 授權後點擊「觀看廣告並開通提醒」，完整觀看一次才提交開通。廣告取消、無廣告、載入失敗、回調缺失或 isEnded 不為 true，均不當成完整觀看。
- 未接受的時點保持「未授權」；若用戶只授權部分時點，開通前明示具體覆蓋，例如「本場將提醒 2 次」，成功後不能顯示三次均已開通。
- 已錯過的時點顯示「已錯過」，不補發；例如距開始 2 小時時，只辦理 1 小時與 10 分鐘提醒。到達精確時點也視為已錯過，避免與 worker 競態。
- 若三個時點全已錯過或事件已開始，不再展示可觀看廣告的訂閱操作。
- 同一場已完整觀看並由服務端確認後，補授權、網路重試、取消後重新開通尚未發送的提醒，不要求重看廣告；權益不可轉移至另一場。
- 本機保存未確認的操作 ID 與完成回調紀錄，回前景或重開時向服務端查詢。未確認期間顯示「正在確認」，不當成成功，也不直接要求重看。
- 該場尚未發送的提醒由列表原處開關直接取消；待辦及部分開通等具體狀態由該場訂閱操作浮層承載。
- 通知內容包括流行類型、海域、開始時刻、此次提前量，保留「依週期預測，實際狀態以遊戲為準」語義；點擊消息返回該場詳情。

## 4. 事件與權限記錄

- 沿用事件鍵 `zoneId:eventTypeId:triggerAtUnixSeconds`，內部全用 Unix 秒；東八區僅負責展示。
- 一位用戶同一場僅一個訂閱主記錄，每個提前量僅一項任務。操作 ID、用戶、事件、提前量、授權登記代數共同用於冪等判斷。
- OpenID 僅從雲函數微信上下文取得；不接受前端指定收件者、通知內容、任意模板、任意發送時間或廣告位。
- 微信的一次性發送次數是平台權限；應用內只把本次成功授權登記到明確時點，不能用 getSetting 的 accept 推導剩餘次數，也不能把一次 accept 複製三次。
- 授權回調只在前端產生，不把前端上報當成微信服務端的密碼學證明。真實可發送狀態以微信接口結果為準；43101 等錯誤須回寫到對應任務。
- 服務端建立與完成廣告會話，綁定用戶、事件、操作 ID，檢查重放、事件有效性及合理順序。官方所核對的普通小程序廣告接口只提供前端完成回調；這些防重措施不能證明不可偽造觀看，不宣稱已有服務端驗簽能力。
- 若當前帳號另外提供正式可用的廣告服務端驗證能力，須先核對文檔與後台配置，再將可信驗證納入設計。

## 5. 雲端架構與資料來源

- 新增專用 runtime service，供頁面查詢配置、建立流程、登記授權、確認開通、列出及取消訂閱；頁面不直接呼叫 wx.cloud 或資料庫。
- 新增提醒業務雲函數與獨立排程 worker，防止前端偽造定時觸發來源；worker 僅由可信排程入口執行。
- 雲端參照資料從 `data/master/major-events.json` 透過現有生成流程產生到各自部署包；禁止手抄一份週期、錨點或海域相位資料。
- 服務端重新計算事件合法性，遵循現有海域延遲與同時事件最多兩類的順序規則；與前端以相同測試向量比對。
- 保存日程資料版本指紋。排程前按當前權威資料重新驗證；事件已變更時停止舊任務並顯示原因，不悄悄改成另一場。
- 集合按用戶＋事件／提前量設唯一約束，待發任務設狀態＋下次執行時間索引；資料庫僅服務端可讀寫。讀取、翻頁、單次批次與用戶待辦量均設上限。
- 建議每位用戶最多 20 場未完成訂閱；操作紀錄與終態任務保留 30 天後由有界清理任務刪除，廣告權益在事件開始後失效。

## 6. 發送與失敗恢復

- 每分鐘掃描到期任務，保存發送前狀態與嘗試紀錄；分頁、有界批次、租約與原子領取防止重疊 worker 重複發送。
- 每個時點允許最多 5 分鐘的排程恢復窗口，且絕不超過事件開始時間；超過窗口標記「已錯過」，避免故障恢復後集中補發。
- 一分鐘排程存在粒度與微信投遞延遲，產品不承諾秒級準時或手機一定響鈴。
- 同一用戶同一模板的發送串行化；對明確未受理的可重試錯誤採有界退避，並在窗口內再次驗證狀態。
- 微信返回 errcode 0 僅記作「已提交微信」，不宣稱用戶已看到；拒收、模板封禁、參數錯誤等有明確失敗狀態。
- 對請求超時、進程在外部發送後崩潰等結果不明情形標記「發送結果待確認」。發送接口無已核實的業務冪等鍵，不能承諾跨系統 exactly-once，不能因租約過期就盲目重發。
- 取消操作原子停用尚未開始發送的任務；已進入外部發送的任務需提示「已開始發送，可能仍會收到」，不能宣稱能撤回微信消息。
- 進行廣告／授權操作時鎖定該場快照；切換詳情、分鐘刷新、頁面卸載、延遲回調均不得將結果寫到另一場。
