## 選擇與邊界

採用同一倉庫的兩個維護分支及固定目錄入口。相比複製兩套獨立倉庫，保留共同歷史，公共修正可用 cherry-pick 同步；相比每次手改 AppID，兩個工作區各自固定帳號，減少誤傳。維護期間不要求兩個分支保持完全相同，也不自動雙向合併。

- 舊端：`codex/phase-20261103-old-maintenance`，由 `e5765d09cf7bfde2aad1064dacc4770b26e48471` 建立；AppID `wx8f961bcd8b26996a`。
- 新端：保留現有 `codex/phase-20261102-miniprogram-migration` 及全部未提交遷移內容；AppID `wxd0bc7afdc9cd334a`。不另複製一份未提交候選造成分叉。
- `E:\AI-UWO-old`、`E:\AI-UWO-new` 為穩定目錄聯結；真實舊工作區由 Codex worktree 管理，新工作區仍是 `E:\AI UWO assistant`。不得歸檔仍被固定入口使用的 worktree。
- `main` 暫不移動，不作兩個帳號間切換開關。分支、工作區、微信開發版本及線上版本分開記錄。

## 發布防錯

新增純只讀工具 `tools/release/check-target.ts`，要求明確選擇 old/new，校驗工作區為 Git 根目錄、AppID、維護分支、完整提交 SHA、tracked/untracked 乾淨狀態及 Node 22。未提交候選、未知目標、錯誤帳號／分支、detached HEAD 都不允許通過。成功僅表示帳號與版本靜態匹配，不能取代 npm run verify、頁面／真機驗收或微信審核。

工具不切換 AppID、不提交、不上傳、不部署；舊端可調用新端工具並明確傳入舊 project-root，兩邊暫時不需要複製或提交同一份工具。發布前先保存工具輸出的 JSON，另以正式上傳結果補足版本記錄。

## 代碼與雲端流程

單端修改從對應維護分支建立短期工作分支，完成驗證及提交後回到對應維護分支。兩端共用修正獨立提交，審核後 cherry-pick；不可同步 project.config.json 的帳號差異，不可盲目整分支互合。master 資料變更仍走唯一數據源及生成鏈。

兩端共用 `cloud1-d7gxfuxfe813b4eaa`。共享雲端以新端遷移後的兼容實現為基礎；舊端 e5765d0 的函數不能整包覆蓋線上兼容版本。雲函數與前端各自記錄部署來源及 hash；本輪不再次部署、不改數據、不恢復新端暫停功能。

## 驗證與完成條件

對發布檢查做紅綠測試，覆蓋兩個正確帳號及錯配、錯分支、未提交／未追蹤、非根目錄、未知目標、Node 版本。舊端加入本輪文件前，以乾淨 e5765d0 基線檢查應通過；兩端加入本輪未提交文件後均應明確拒絕。固定入口與原目錄逐一核對真實路徑、AppID、Git 狀態；原遷移文件及必要 ignored 輸入 hash 不變。

新增工具只在 Node 執行，不改小程序共享 runtime、畫面或包大小。完整門禁在乾淨隔離候選執行，原工作區歷史 ignored 腳本缺陷不夾帶修復。最後列明變更、檢查及擬用 commit message，等待用戶確認後才提交；不推送、不審核、不發布。
