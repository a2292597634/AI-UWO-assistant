# 兌換碼入口與玩家設定 UI 修正設計

**日期：** 2026-09-08  
**狀態：** 已實作，待整合

## 背景

目前兌換碼功能有三個直接影響使用者操作的問題：首頁「兌換碼」入口沒有正式圖標、玩家設定頁的三個操作按鈕縱向排列且視覺占高過大、設定表單要求使用者額外輸入與遊戲暱稱重複的「設定名稱」。

## 目標

1. 讓首頁兌換碼入口顯示與既有航海士／艦隊入口一致的本地圖標。
2. 降低兌換相關頁面的按鈕視覺占高；保存、確認刪除與確認領取等主要操作保留至少 `88rpx` 的實際觸控熱區，列表與切換等輔助操作使用既有 compact 變體。
3. 移除獨立設定名稱輸入，直接以遊戲內暱稱作為玩家設定的顯示名稱。
4. 舊版本已保存的資料可正常讀取，不要求使用者重新建立設定。

## 非目標

- 不修改官方伺服器清單、兌換流程、CloudBase 代理或資料流水線。
- 不改動其他首頁入口的內容與路由。
- 不新增依賴，不在小程序 Runtime 引入遠端資源或網路請求。

## 設計

### 首頁入口圖標

新增 `feature-coupon` 本地圖標素材，放入既有 `data/master/ui-assets` → `miniprogram/assets/ui` 的生成鏈。素材為 96×96 的小尺寸航海風兌換券圖標，沿用既有深色底、金色邊框與低色數處理；生成配方限制在 feature 素材預算內。首頁 `coupon-redemption` module 改用 `/assets/ui/feature-coupon.png`，並保留現有載入失敗回退，避免素材異常時入口消失。

### 按鈕尺寸與排列

設定列表的「使用／編輯／刪除」改為卡片底部的水平操作列，採用既有 `.ui-button--compact` 變體，避免三個按鈕縱向堆疊造成卡片過高。保存與確認刪除仍使用完整主要操作熱區。

兌換頁的「切換」及空狀態「新增玩家設定」沿用次要按鈕變體並套用 `.ui-button--compact`；固定底部的「確認並領取」仍是唯一主要操作與 `88rpx` 熱區，僅移除多餘高度與過大留白。

### 玩家設定資料

`CouponProfileInput` 不再要求 `name`；輸入只包含 `gameServerId` 與 `userNo`。Store 在正規化時以修剪後的 `userNo` 同時寫入 profile 的 `name`，以維持既有儲存結構與其他頁面的顯示介面。讀取舊資料時接受舊版 `name` 欄位，但回傳的 profile 會以 `userNo` 作為 `name`，因此舊設定名稱會自動被暱稱取代；不需清除或手動遷移本機資料。

設定頁表單只保留官方伺服器 picker 與遊戲內暱稱輸入；編輯時從 profile 帶入伺服器與暱稱，保存新增／修改均由暱稱產生顯示名稱。刪除確認文案也改為顯示暱稱。

## 測試與驗收

- Contract／store 測試：輸入型別不再包含 `name`；新增與更新後的 profile `name` 等於修剪後暱稱；舊格式資料載入後 `name` 以暱稱為準。
- 頁面測試：設定頁 WXML 不含「設定名稱」欄位；保存 payload 只有伺服器與暱稱；首頁 module 指向新圖標；設定操作列與兌換頁輔助按鈕使用 `ui-button--compact`，保存、確認刪除與確認領取仍具 `88rpx` 熱區。
- 兌換碼頁首次進入時預填 `FULLMOON2026`；此值只存在頁面輸入，不寫入本機設定，提交完成後照既有流程清空。
- UI 素材測試：`feature-coupon` 有對應 recipe、輸出檔與報告，feature 群組及主包體積門禁通過。
- 完成後執行 `npm run verify` 與 `git diff --check`，並在微信開發者工具確認首頁入口、按鈕排列及舊資料兼容。
