# 航海士資料投稿與審核工作台設計規格

- 日期：2026-09-04
- 分支：`codex/phase-11-資料投稿審核`
- 設計狀態：已完成需求確認與設計確認，等待實作計畫

## 1. 背景

現有「資料維護」頁是面向熟悉資料庫結構的新增航海士編輯器。使用者需要在同一個長表單中理解基本資料、技能組別、來源 ID、招募關係與內部欄位，職業、國籍和技能還需要先搜尋再操作 picker。這使一般使用者難以完成投稿，也沒有清楚的投稿狀態、審核入口或審核後回饋。

現有 CloudBase 記錄雖然已預留 `pending`、`approved`、`rejected` 狀態，但目前缺少真正的管理員審核 action；`listAll()` 會返回 `pending` 與 `approved`，投稿成功後頁面也會直接把資料寫入本地自訂航海士快取。這些行為不符合「先審核、再發布」的目標。

本次 Change 將資料維護改造成「所有使用者可投稿、單一管理員在小程序內審核、通過後經資料流水線發布」的閉環。

## 2. 已確認的目標

1. 所有使用者都可以提交完整的航海士資料。
2. 投稿表單不要求使用者理解 ID、Canonical 結構、技能組別或槽位。
3. 投稿頁採兩步流程，降低一次看到完整長表單的壓力。
4. 技能只能從篩選結果中選擇，不允許自由輸入技能名稱。
5. 解鎖等級預設為 `1`，使用者可以逐筆修改。
6. 使用者必須上傳正式版航海士頭像。
7. 招募資料為選填項。
8. 不要求使用者填寫證明資料、Boss 標記、招募備註、來源網頁 ID 或來源連結。
9. 使用者可以查看自己的投稿狀態與駁回原因。
10. 目前只允許一個指定微信帳號進入審核工作台，但權限邊界要能擴展到多人。
11. 管理員可以直接修改投稿資料，再保存或通過。
12. 審核通過不等於立即進入名鑑；只有同步、生成和發布後才進入正式資料。
13. `archive/` 保持唯讀；`data/master/` 仍是正式資料唯一手動維護來源；`miniprogram/generated/` 只由工具生成。

## 3. 範圍與非目標

### 3.1 本次範圍

- 將既有資料維護入口改為新增航海士投稿流程。
- 新增使用者自己的投稿列表與狀態查詢。
- 新增管理員待審核列表與投稿詳情編輯頁。
- 擴充既有 `officer-custom` CloudBase service／repository 的投稿、審核、發布狀態與權限 action。
- 讓同步工具只匯出已審核資料，並處理已審核頭像素材。
- 修正未審核資料進入 runtime 快取的邊界。
- 增加投稿、審核、狀態流轉、權限與同步的測試。

### 3.2 不在本次範圍

- 不新增證明截圖、來源連結、Boss 標記、招募備註或來源 ID 欄位。
- 不讓使用者自由輸入技能、職業、國籍、城市、條件或前置航海士的內部 ID。
- 不在審核通過後立即以 CloudBase 動態資料取代正式生成資料。
- 不新增多人管理員的管理 UI；只預留伺服器端管理員列表／角色介面。
- 不新增投稿留言、公開投票、通知推送、社交功能或投稿排行榜。
- 不新增依賴、遠端 URL、運行時網路入口或新的資料來源。
- 不修改與投稿／審核流程無關的頁面、資料、素材或 Cloud Function。
- 第一版不提供雲端草稿；兩步之間可返回修改，離開未提交的頁面不建立投稿記錄。

## 4. 整體資訊架構

保留首頁現有「資料維護」入口，進入後直接開始新增投稿，不增加多餘的中轉首頁。

### 4.1 使用者入口

`/pages/officer-editor/index` 保留為投稿入口，頁面頭部提供：

- `新增投稿`：預設工作區。
- `我的投稿`：進入目前微信帳號自己的投稿列表。
- `審核工作台`：只有管理員帳號顯示；即使前端未顯示，服務端仍要再次驗證權限。

新增頁可拆出以下頁面以隔離責任：

- `pages/officer-submissions/index`：使用者自己的投稿列表。
- `pages/officer-review/index`：管理員待審核列表。
- `pages/officer-review-detail/index`：管理員單筆投稿詳情與編輯。

實作可以保留現有投稿頁路徑，降低首頁與既有導航變更；投稿列表和審核工作台不與原長表單共用不必要的頁面狀態。

### 4.2 投稿工作區

投稿頁使用「第 1 步／共 2 步」進度提示：

1. 基本資料與正式頭像。
2. 語言、技能與選填的招募資料。

第二步完成後先顯示唯讀摘要，再提交到 CloudBase。提交成功後回到「我的投稿」或顯示進入該筆投稿詳情的入口。

## 5. 使用者投稿流程

### 5.1 第一步：基本資料

使用者必須填寫：

| 欄位 | 操作方式 | 規則 |
| --- | --- | --- |
| 航海士名稱 | 文字輸入 | 不可為空，保留既有長度校驗 |
| 稀有度 | 選擇器 | 只能選字典中的稀有度 |
| 類型 | 選擇器 | 只能選字典中的類型 |
| 性別 | 選擇器 | 只能選字典中的性別 |
| 職業 | 關鍵詞篩選後選擇 | 不允許輸入職業 ID |
| 國籍 | 關鍵詞篩選後選擇 | 不允許輸入國籍 ID |
| 正式版頭像 | 相冊選擇 | 必須有一張有效圖片 |

不顯示或要求：Boss 標記、來源 ID、來源連結、維護備註。

點擊「下一步」時，在對應欄位附近顯示缺失原因；不把所有錯誤只放在 toast。

### 5.2 第二步：能力資料

#### 語言能力

- 使用者從本地語言字典選擇語言。
- 每筆填寫語言等級。
- 相同語言不可重複。
- 至少新增一筆語言能力。
- 語言等級使用數值控制或固定選項，沿用既有合法範圍。

#### 技能

- 使用者先輸入關鍵詞，再從篩選結果中選擇技能。
- 沒有篩選結果時顯示「找不到符合的技能」，不允許直接建立未知技能。
- 相同技能不可重複。
- 每筆技能顯示技能名稱、解鎖等級與技能等級。
- 解鎖等級預設 `1`，使用者可以單獨修改每筆技能。
- 技能等級沿用既有合法範圍，預設值沿用現有行工廠的 `1`。
- 不顯示 `sk0`～`sk5`、主動／被動組別或槽位；這些欄位由系統和審核者處理。
- 至少新增一筆技能。

#### 招募資料

- 整段預設收起並標示「選填」。
- 使用者有資料時才展開填寫。
- 招募城市、招募條件和前置航海士均從已有字典／名鑑中篩選選擇。
- 不要求招募資料非空；未填寫要以明確狀態表示，不轉換成假 ID。

### 5.3 頭像限制

目前正式運行頭像 627 張約為 `2.6–13 KB`，現有兩張自訂頭像源文件約 `89–110 KB`，尺寸約 `222×202` 和 `258×243 px`。為兼顧手機原圖與運行時負載，投稿頭像規則定為：

- 每筆投稿只允許一張頭像。
- 支援 PNG、JPG、JPEG。
- 用戶端先壓縮；實際提交檔案不得超過 `512 KB`。
- 最長邊不超過 `512 px`，保留原始比例，不強制裁切。
- 建議尺寸為 `256–512 px`。
- 服務端再次檢查 MIME／檔案簽名、尺寸與檔案大小。
- 選擇後顯示檔案大小，例如 `已選擇 96 KB / 512 KB`。
- 超過限制時阻止提交，保留其他已填寫資料，提示重新選擇或壓縮圖片。

正式頭像檔案與投稿資料同一筆記錄關聯；同步發布時再轉為正式資料資產，不要求使用者理解 CloudBase file ID。

### 5.4 提交前確認與成功結果

提交前摘要顯示：

- 基本資料摘要。
- 語言數量與名稱。
- 技能數量、名稱、解鎖等級和技能等級。
- 頭像預覽與檔案大小。
- 招募資料是否填寫。

提交成功後：

- 顯示「已提交，等待審核」。
- 只建立 `pending` 投稿記錄。
- 不呼叫 `addCachedCustomOfficer`，不把投稿立即加入任何名鑑快取。
- 提供「查看我的投稿」入口。

## 6. 我的投稿

使用者只能讀取由服務端 `OPENID` 對應的投稿記錄，不能傳入或指定其他 `ownerUid`。

列表每筆顯示航海士名稱、頭像、提交時間、技能數量與狀態：

- `待審核`：等待管理員處理。
- `已審核，待發布`：管理員已通過，等待資料同步與小程序發布。
- `已發布`：已進入目前正式資料版本。
- `已駁回`：顯示駁回原因。

已駁回投稿可以「根據原因修改後再次提交」。再次提交以同一 `submissionId` 建立遞增的 `revision`，保留原 revision 的唯讀資料與審核歷史；投稿列表只顯示最新 revision，管理員仍可查看歷史版本和原本的駁回原因。

列表需要區分載入中、空列表、載入失敗和正常結果；載入失敗提供重試，不顯示成空列表。

## 7. 審核工作台

### 7.1 待審核列表

管理員進入後預設顯示 `待審核`，按提交時間倒序排列。每行顯示：

- 頭像。
- 航海士名稱。
- 投稿時間。
- 技能數量。
- 招募資料是否填寫。
- 狀態。

列表提供以下篩選：

- 待審核。
- 已審核，待發布。
- 已駁回。
- 已發布。

列表狀態需要區分載入中、空列表、錯誤和正常資料。待審核數量可以顯示於頁面標題，但不能只用顏色表達狀態。

### 7.2 單筆詳情與編輯

詳情頁沿用投稿端的分組，但改為管理員可編輯：

1. 基本資料。
2. 語言能力。
3. 技能列表。
4. 招募資料。
5. 正式頭像。

管理員可以：

- 修正名稱、字典選項、語言等級、技能等級與解鎖等級。
- 替換不合格或錯誤的正式頭像。
- 為每筆技能選擇主動／被動類型與資料組別。
- 調整技能槽位；同一組別的槽位要由 presenter／domain 給出清楚提示，避免重複。
- 查看系統生成的航海士 ID、`visualGradeId` 和發布前 Canonical 預覽。
- 保存修改但維持 `待審核`。

內部欄位只在此頁顯示，普通使用者不可見。

### 7.3 審核操作

底部固定操作區包含：

- `保存修改`：保存管理員修正，狀態仍為 `pending`。
- `通過，等待發布`：保存最終審核資料，狀態變為 `approved`，前端顯示「已審核，待發布」。
- `駁回投稿`：打開原因輸入流程；沒有駁回原因不得完成操作。

每次修改、通過、駁回和標記發布都記錄管理員、時間、動作與必要原因，形成可追蹤的審核歷史。

### 7.4 權限

- 管理員判斷必須在 Cloud Function 服務端完成。
- 第一版只在管理員白名單中配置一個微信 `OPENID`；實際值不得寫入前端或提交資料。
- 權限判斷抽象為 `isOfficerAdmin(openid)` 或等價服務介面，後續可改為多帳號白名單／角色集合而不改 action 語義。
- 非管理員不能列出全部投稿、讀取他人投稿、修改投稿、通過、駁回或標記發布。

## 8. 投稿資料模型與狀態

沿用既有 `custom_officers` 集合，擴充為投稿與發布記錄；既有記錄在部署時依遷移腳本補齊狀態、revision 與審核欄位，無法識別或無法安全遷移的舊記錄必須先停留在隔離狀態，不得直接進入正式名鑑。前端不可直接提交完整 CanonicalOfficer。

### 8.1 記錄概念

```ts
interface OfficerSubmissionRecord {
  _id: string
  submissionId: string
  ownerUid: string
  status: 'pending' | 'approved' | 'rejected' | 'published'
  revision: number
  formData: {
    name: string
    rarityId: string
    typeId: string
    genderId: string
    jobId: string
    nationalityId: string
    languages: Array<{ languageId: string; level: number }>
    skills: Array<{ skillId: string; unlockLevel: number; level: number }>
    recruitment: {
      cityIds: string[]
      requirementId: string | null
      requiredOfficerIds: string[]
      note: string | null
    }
    portraitFileId: string
  }
  canonicalData: Record<string, unknown> | null
  review: {
    reviewerUid: string | null
    reviewedAt: string | null
    rejectReason: string | null
  }
  publish: {
    datasetVersion: string | null
    publishedAt: string | null
  }
  history: Array<Record<string, unknown>>
  createdAt: string
  updatedAt: string
}
```

### 8.2 服務端規則

- `ownerUid` 只使用 Cloud Function 的 `OPENID`，不信任客戶端傳值。
- 使用者提交時只接受白名單內的字典 ID、技能 ID、等級與頭像檔案資訊；未知欄位丟棄或拒絕。
- `canonicalData` 由服務端／審核流程依 `formData` 建構或重建，不接受使用者直接覆蓋。
- `submissionId` 建立後固定；航海士內部 ID 由系統根據 submission 建立並保持穩定，不因管理員修正名稱而變更。
- `visualGradeId` 預設由稀有度推導；特殊資料由管理員在審核端確認。
- `displayOrder` 不在使用者投稿階段分配，發布同步時依正式資料規則計算。
- 由於使用者不填來源 ID，正式資料的 `sourceRefs` 應改為支持投稿來源，例如 `{ submissionId }`；不能以不存在的 `voyageTw` 假裝來源。
- 既有正式資料中需要保留的 `portraitId`、素材路徑與 CloudBase file ID 在同步／資產流程中完成轉換。

### 8.3 狀態轉移限制

| 目前狀態 | 可執行動作 | 下一狀態 |
| --- | --- | --- |
| `pending` | 管理員保存修改 | `pending` |
| `pending` | 管理員通過 | `approved` |
| `pending` | 管理員駁回 | `rejected` |
| `rejected` | 使用者重新提交 | 新 revision 的 `pending` |
| `approved` | 同步前管理員修正 | `approved` |
| `approved` | 發布完成後標記 | `published` |
| `published` | 新資料修訂 | 新 revision 的 `pending` 或另開更新投稿 |

不允許普通使用者直接將狀態改為 `approved` 或 `published`。`pending`、`rejected` 不可被發布同步讀取。

## 9. 發布與資料流水線

審核工作台只負責把資料變成「可發布」，不直接修改工作區的 `data/master` 文件，也不直接改動生成資料。

```text
小程序投稿
  → CloudBase pending
  → 管理員在小程序修改／通過
  → CloudBase approved
  → sync:custom-officers 只同步 approved
  → data/master/custom-officers.json
  → npm run data:check
  → npm run data:generate
  → npm run verify
  → 發布小程序
  → 標記 published + datasetVersion
```

同步工具需要：

- 使用管理憑證取得 `approved` 記錄，不再使用會返回 `pending` 的 `listAll` 語義。
- 下載／整理已審核投稿的正式頭像到資料資產 staging，再由既有資產流水線處理。
- 將人類欄位轉為符合 `data/master` schema 的正式資料。
- 生成穩定的來源引用、內部 ID、`displayOrder` 和必要維護資訊。
- 只在同步、資料檢查、生成和發布準備成功後，才允許標記相應記錄為 `published`。

runtime 名鑑只能讀取正式生成資料。既有自訂航海士快取若保留，至少只能包含 `published` 記錄；投稿成功後不可直接寫入快取。

## 10. 錯誤與安全邊界

### 10.1 使用者端

- 未登入：提示需要登入，保留目前頁面輸入。
- 字典或技能選項載入失敗：顯示重試，不渲染成空選項而讓使用者提交錯誤 ID。
- 頭像不符合大小、尺寸或格式：顯示具體限制，保留其他資料。
- 提交網路失敗：保持當前資料與可重試狀態，不顯示成功。
- 重複投稿：服務端依既有資料與待審核投稿做檢查，返回可理解的提示；不以 ID 隨機化掩蓋重複資料。

### 10.2 管理員端

- 非管理員訪問任何審核 action 都返回安全的無權限結果。
- 投稿已被更新時使用 revision／updatedAt 檢查，避免覆蓋較新的版本。
- 駁回沒有原因時拒絕 action。
- Canonical 轉換、技能組別或資產處理失敗時保持 `pending` 或 `approved` 的可恢復狀態，不標記成成功。
- 同步或生成失敗時維持「已審核，待發布」，不標記 `published`。
- 所有錯誤同時提供可見文字與下一步，不只使用顏色或 toast。

## 11. 元件與程式責任

### 11.1 投稿頁

- Page Controller 負責步驟切換、頁面輸入和導航。
- Presenter 負責分步視圖、欄位錯誤、摘要、技能篩選結果與投稿狀態文案。
- Domain／contract 負責人類欄位的完整性、重複技能／語言、等級與頭像 metadata 校驗。
- Service 只負責投稿 action，不讓頁面直接呼叫 CloudBase。

### 11.2 我的投稿頁

- 只透過 `listMine` 讀取服務端依 OPENID 過濾的記錄。
- 狀態、駁回原因和重新提交入口由 presenter 生成。
- 不讀取正式生成資料以外的他人投稿內容。

### 11.3 審核頁

- 只透過 admin service 取得列表、詳情、保存、通過、駁回和發布標記結果。
- 管理員編輯可以沿用投稿端的選擇元件，但額外顯示技能組別、槽位與 Canonical 預覽。
- 審核頁不直接操作 repository，也不把管理員權限判斷放在 WXML 或 PageData。

## 12. 測試策略

所有資料解析、轉換、校驗、狀態流轉、同步篩選和確定性生成遵循紅—綠—重構。

### 12.1 Domain／Presenter

- 必填基本欄位、至少一種語言、至少一項技能與必須頭像。
- 職業、國籍和技能只接受字典／技能選項中的 ID。
- 技能與語言不可重複。
- 技能解鎖等級預設 `1` 且每筆可修改。
- 招募資料完全選填，未填不產生假 ID。
- 投稿步驟、摘要、錯誤定位和狀態文案正確。
- 長名稱、長技能名稱與駁回原因可換行。

### 12.2 Cloud Function／Repository

- owner 只能來自 server context；客戶端 owner 欄位被忽略。
- 只有白名單管理員能執行 admin action。
- 使用者只能列出自己的投稿。
- `pending`、`rejected` 不被發布列表返回。
- `approved` 才能進入同步列表。
- 保存、通過、駁回、重新提交和標記發布遵守狀態轉移規則。
- 駁回原因必填，版本衝突可恢復。
- 不接受客戶端直接覆蓋 canonicalData、status、review、publish 或 ownerUid。

### 12.3 同步與資料契約

- 同步腳本只匯出 `approved`。
- 同步輸出的 `custom-officers.json` 通過 schema、資料審計與生成檢查。
- `sourceRefs` 支持投稿來源而不要求使用者填寫 voyage.tw ID。
- 頭像下載、檔案大小、資產路徑和生成資料保持確定性。
- 生成結果未改變時，`generate:check` 沒有 diff。

### 12.4 UI 與人工驗收

在 320／375／393／430px 驗證：

- 普通使用者能在兩步內完成完整投稿，不會看到技術 ID 或技能組別。
- 技能必須篩選後選擇，無法自由輸入未知技能。
- 頭像大小提示、壓縮、預覽、替換和失敗重試可用。
- 我的投稿能正確顯示待審核、已審核待發布、已駁回與已發布。
- 管理員看到待審核列表，進入詳情後可修改，再保存或通過。
- 駁回原因能回到使用者端；重新提交會形成新 revision。
- 待審核資料不出現在正式名鑑；同步發布後才可查詢。
- 所有固定底部操作包含安全區留白，沒有頁面級橫向溢出。

## 13. 工程門禁與交付

- 不修改 `archive/`。
- 不手動修改 `miniprogram/generated/`；生成資料只由 `npm run data:generate` 產生。
- `data/master/` 只接受同步工具輸出的正式投稿資料與既有人工維護資料。
- 不新增或升級依賴。
- 不在小程序頁面新增 `wx.request`、遠程 URL 或 Node.js API；CloudBase 呼叫集中於既有 service 邊界。
- 實作完成後執行 `npm run verify`、`git diff --check`，以及 Cloud Function、同步、資料與頁面相關測試。
- 完成產品實作後，先展示變更文件、驗證結果、人工驗收結果與擬用 commit message，未經使用者確認不提交產品實作 commit。

## 14. 完成條件

只有同時滿足以下條件才算完成：

1. 普通使用者可以在兩步流程內提交完整基本、語言、技能與頭像資料。
2. 技能只能透過篩選選擇，解鎖等級預設為 `1` 並可逐筆修改。
3. 招募資料保持選填，使用者不需填證明、Boss、來源或維護技術欄位。
4. 投稿狀態與駁回原因可由投稿者查看。
5. 只有指定管理員能在小程序工作台查看、修改、通過或駁回投稿。
6. 審核通過後資料只進入待發布隊列，不立即污染 runtime 名鑑。
7. 同步工具只把已審核資料導入 `data/master`，生成與發布後才顯示在名鑑。
8. 頭像遵守單張、PNG／JPG／JPEG、512 KB、512 px 長邊限制。
9. 權限、狀態、同步、資料 schema、頁面流程與窄屏驗收全部通過。
