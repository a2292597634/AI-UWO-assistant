## 0. 后续 Agent 使用说明

本报告是后续 UI/UX 改造的决策基线。发生冲突时，按以下顺序判断：

1. 业务正确性与编队数据安全；
2. 状态可解释、操作可确认和可撤销；
3. 微信小程序窄屏可用性；
4. 全局一致性与信息层级；
5. 游戏氛围和局部视觉表现。

后续实现必须遵守仓库 `AGENTS.md`：

- 所有 UI 文案使用繁体中文；
- 不直接修改 `archive/` 和 `miniprogram/generated/`；
- 不新增、删除或升级依赖，除非另行获得用户确认；
- 不在小程序运行时代码中新增 `wx.request`、`wx.cloud`、远程 URL 或 Node.js API；
- 数据解析、转换、校验、筛选和 Solver 逻辑遵循 TDD；
- 每个 Change 使用独立 `codex/phase-N-描述` 分支；
- Commit 前运行 `npm run verify`，并向用户展示变更文件、验证结果和拟用 Commit Message，等待确认。

## 1. 最终结论

当前产品已经具备较完整的资料查询、技能查看、战斗配队、冒险配队和配置保存能力，主题方向也基本成立：羊皮纸底色、深墨色面板、黄铜点缀、港口主视觉与航海士素材，已经能传达“大航海资料馆”的产品气质。

主要问题不是“不够漂亮”，而是：

1. 冒险自动配队存在可能清空非锁定成员的 P0 业务风险；
2. 自动配队结果直接覆写当前编队，没有预览、取消和撤销；
3. 锁定、移除、本船排除、全队排除、跨船移动的语义没有被界面准确表达；
4. 手机窄屏上塞入过多微型按钮、重复摘要和嵌套面板；
5. 页面之间缺少真正的 Design System，像由数套相似但不相同的界面拼接而成；
6. 视觉优化必须建立在业务流程重构之后，不能先做全量换肤。

最终建议：

> 不进行推倒式重设计。保留现有功能、主题方向和数据结构，按“业务安全 → 结果确认机制 → 操作语义 → 信息架构 → Design System → 视觉资产”的顺序渐进改造。

## 2. 当前整体设计评价

| 维度         | 评价 | 结论                                                    |
| ------------ | ---- | ------------------------------------------------------- |
| 功能完整度   | 较好 | 已形成可用的资料查询和配队工具基础                      |
| 业务逻辑表达 | 较弱 | Domain 状态未被 UI 准确解释，自动配队缺少安全确认       |

## 3. 优先级定义

| 等级 | 含义                                                 | 处理要求                           |
| ---- | ---------------------------------------------------- | ---------------------------------- |
| P0   | 可能造成错误结果、编队意外丢失或核心流程无法完成     | 必须最先独立修复，不与视觉改版混合 |

## 4. 最主要的 10 个问题

### 4.1 P0：冒险自动配队目标流程存在断点和误清空风险

**现状**

- 新舰队会自动加入一批 Lv.0 默认目标，并直接进入自动模式；
- “新增目标”只添加一个 `skillId: null` 的目标；
- 自动模式下技能选择器被隐藏，新增的空目标没有后续配置入口；
- 全部目标为 Lv.0 时，有效求解目标为空；
- 点击“重新计算”后仍继续进入“仅保留锁定航海士”的覆写路径。

关键代码：

- `miniprogram/pages/adventure-fleet/index.ts` 中的 `initDefaultTargets`、`onAddTarget`、`onRecalculate`；
- `miniprogram/pages/adventure-fleet/index.wxml` 中仅手动模式显示的技能选择器。

**原因**

用于“统计追踪”的 Lv.0 技能和用于“自动求解”的优化目标混在同一数据结构和界面中；目标编辑入口只为手动模式设计。

**用户影响**

- 用户新增目标后无法完成配置；
- 用户可能在无有效目标时意外丢失全部非锁定成员；
- 用户无法理解 Lv.0 目标是否参与自动配队。

**优化建议**

- “新增目标”必须立即打开技能选择 Bottom Sheet；
- 选择技能后直接创建 Lv.1 优化目标；
- 没有任何 `targetLevel > 0` 的目标时，计算按钮必须禁用；
- Lv.0 技能移动到“技能追踪”区域，不参与 Solver；
- 自动计算只能生成待确认方案，不得直接修改舰队。

### 4.2 P0：自动配队结果直接应用，没有预览、取消或撤销

**现状**

战斗和冒险页面在 Solver 返回后立即调用重算并渲染，用户无法在状态变更前检查成员变化和技能收益。

**原因**

求解结果被直接视为最终状态，而不是一份待确认的方案。

**用户影响**

- 无法判断哪些成员会被移除或替换；
- 无法判断目标是否真正提升；
- 无法取消或恢复到计算前状态。

**优化建议**

建立统一的“计算方案 → 预览差异 → 用户应用”事务流程：

- 计算只生成不可变 Proposal；
- 预览显示目标达成、成员新增/移除、锁定成员和约束冲突；
- 取消预览不改变当前状态；
- 应用后提供一次撤销。

### 4.3 P1：锁定、移除、排除和移动的语义不清

**现状**

- 当前“移除”会写入 `removedOfficerIds`；
- `removedOfficerIds` 在当前船下次求解时作为排除条件；
- 页面没有展示或管理这份本船排除名单；
- 其他船成员在候选列表中看起来是禁用状态，但实际上仍可点击移动。

**原因**

Domain 中存在多个不同约束状态，但 UI 将它们压缩成“锁定 / 移除 / 排除”三个微型按钮。

**用户影响**

用户不知道一次操作是临时调整、当前船约束还是全局约束，也不知道航海士为什么没有再次出现。

**优化建议**

统一为五种明确语义：

| 操作         | 业务语义                         |
| ------------ | -------------------------------- |
| 锁定         | 后续计算必须保留                 |
| 移出本次结果 | 仅从当前结果移除，下次仍可被推荐 |
| 本船排除     | 当前船后续计算不再推荐           |
| 全舰队排除   | 所有船均不再推荐                 |
| 移动到其他船 | 显示来源船，并在执行前确认       |

现有 `removedOfficerIds` 应被正式命名和展示为“本船排除”，不能继续作为隐藏约束。

### 4.4 P1：配队页面信息顺序没有围绕真实任务组织

**现状**

标题、配置栏、船标签、当前船标题、成员格、模式、目标、技能选择、候选人、排除名单、技能摘要和全舰队概览依次堆叠，同一状态被重复展示。

**原因**

界面按功能模块逐段追加，没有形成“定义目标—计算—确认—微调—保存”的任务主线。

**用户影响**

页面过长，首屏没有明确焦点，用户需要频繁上下滚动寻找当前任务。

**优化建议**

- 删除微信原生导航下方的重复大型页面标题；
- 配置、当前船、模式和目标状态保持在页面前部；
- 长摘要、技能追踪和约束名单默认折叠；
- 船标签能表达的状态不再在当前船标题和全舰队概览中重复。

### 4.5 P1：窄屏内使用过多微型操作按钮

**现状**

- 战斗页面采用 6 列槽位；
- 每个槽位底部再放 3 个操作按钮；
- 操作文字低至 12–14rpx；
- 冒险页面的 5 列航海士卡也采用类似结构。

**原因**

为了让所有操作永久可见，牺牲了点击热区、文字可读性和视觉层级。

**用户影响**

误触概率高，锁定、移除和排除难以准确点击，成员网格成为页面最嘈杂的区域。

**优化建议**

- 航海士卡整卡可点击；
- 点击后打开 Action Sheet；
- 操作项使用至少 88rpx 高的整行热区；
- 卡片只保留锁定、需复核等状态标记；
- 战斗编队由 6 列调整为 5 列，11 人仍保持三行。

### 4.6 P1：视觉规则相似但没有统一来源

**现状**

- 全局 `app.wxss` 只有基础页面背景和字体；
- 页面内大量重复硬编码颜色、圆角、字号、按钮和弹窗；
- 战斗 WXSS 约 984 行，冒险 WXSS 约 1181 行；
- 冒险样式中约 1075 行内容也出现在战斗样式中。

**原因**

缺少 Design Token、基础组件和统一状态规范。

**用户影响**

同一种“确认”“危险”“选中”“禁用”在不同页面表现不一致，后续维护和改版成本高。

**优化建议**

先建立 Token 规范和共享组件，再逐页替换。只将至少被两个页面使用的模式组件化，避免为了组件化制造更多层级。

### 4.7 P1：资料页导航混合“内容类型”和“筛选维度”

**现状**

顶部五个 Tab 为“航海士、技能、语言、职业、技能清单”。其中技能、语言和职业实际是航海士筛选维度，技能清单则属于另一种内容类型。技能清单页还同时显示航海士搜索和技能搜索。

**原因**

一级导航和筛选没有分层。

**用户影响**

用户难以预测切换 Tab 后是更换内容还是增加过滤条件，筛选控件占用大量首屏空间。

**优化建议**

- 一级内容仅保留“航海士 / 技能”；
- 航海士页只保留一个搜索框；
- 语言、职业、稀有度、类型、性别、技能进入筛选 Bottom Sheet；
- 技能页只显示技能搜索、主动/被动和技能分类。

### 4.8 P1：首屏和安全区域利用不稳定

**现状**

- 首页主视觉高 320rpx；
- 配队页在微信原生标题下再次放大型页面标题；
- 多数页面没有底部安全区处理；
- 只有技能 Sheet 和详情页局部使用安全区。

**原因**

页面将品牌标题、配置状态和业务内容都做成独立大区块。

**用户影响**

小屏首屏看不到核心操作；带 Home Indicator 的 iPhone 可能遮挡底部操作。

**优化建议**

- 首页 Hero 收敛到约 240rpx；
- 配队页依赖微信原生导航标题；
- 配置栏改为紧凑型 Sticky Bar；
- 所有固定底部操作区增加 `env(safe-area-inset-bottom)`；
- 禁止页面级横向溢出。

### 4.9 P2：详情页和编辑页像两套不同产品

**现状**

详情页使用浅色资料馆风格；新增航海士页是完整深色长表单，全部字段同时展开。

**原因**

编辑页更接近内部管理工具，没有接入现有产品设计语言。

**用户影响**

用户从资料页进入维护流程时产生明显割裂，长表单也增加了完成压力。

**优化建议**

- 详情页保留“人物档案 + 技能优先”的结构，仅减少卡片嵌套；
- 编辑页改为“基本资料—能力与语言—技能—确认”的分段或折叠表单；
- “新增航海士”从首页一级入口降级为“资料维护”次级入口；
- 不改变字段、校验和提交能力。

### 4.10 P2：首页及操作图标缺失

**现状**

首页仅航海士资料拥有正式图标，其他模块使用文字回退；锁、删除、排除、相机和菜单混用 Emoji 或 Unicode 字符。

**原因**

尚未形成统一图标资产集。

**用户影响**

产品呈现出功能原型感，跨平台字符样式也不稳定。

**优化建议**

增加本地轻量图标集，并始终配合文字标签。不要通过整页背景图解决完成度问题。

## 5. 配队页面最终重构方案

### 5.1 标准业务流程

```text
载入或新建配置
  ↓
选择作用范围（战斗：当前船；冒险：全舰队）
  ↓
选择手动 / 自动模式
  ↓
定义目标与约束
  ↓
手动选择候选人 / 自动生成方案
  ↓
预览结果与目标达成情况
  ↓
应用方案
  ↓
锁定、移动、排除和微调
  ↓
保存配置
```

界面必须围绕这条流程组织，不能再按代码模块顺序堆叠。

### 5.2 配队页统一骨架

```text
[紧凑配置栏：配置名 · 已保存/未保存 · 保存 · 更多]

战斗页：[船1 8/11 ✓] [船2 11/11 !] [...]
冒险页：[全舰队 54/77 · 已锁定 8]

[手动配队 | 自动配队]

[当前成员网格]
  点击成员 → 航海士操作 Action Sheet

[当前模式工作区]
  手动：选择技能 → 候选航海士与技能贡献
  自动：优化目标 → 计算方案

[本船/全舰队约束] 默认折叠
[技能统计与全舰队概览] 默认折叠

[结果预览 Bottom Sheet]
```

### 5.3 战斗配队

必须实现：

- 保留七艘船和每船十一人的业务结构；
- 船标签显示人数、目标达成和“需复核”状态；
- 手动模式先选技能，再显示候选人；
- 候选人的主信息必须显示实际技能贡献，例如“操帆 +Lv.3”；
- 职业和稀有度降为次要信息；
- 其他船航海士显示“第 3 船 · 点击后移动”，不得使用伪禁用样式；
- 点击成员卡打开操作面板，不在卡片中常驻三个按钮；
- “本船排除名单”和“全舰队排除名单”必须可见、可解除；
- 全舰队摘要默认折叠。

### 5.4 冒险配队

必须把两类目标分离：

1. **优化目标**：Lv.1–Lv.10，参与 Solver；
2. **技能追踪**：Lv.0 或无目标等级，只用于查看当前累计值。

目标工作区：

```text
全舰队优化目标（2）
────────────────
测量       当前 Lv.7 / 目标 Lv.10   [-] 10 [+]
生态调查   当前 Lv.4 / 目标 Lv.6    [-]  6 [+]
────────────────
[＋新增目标]           [计算方案]

技能追踪（25）                     [展开]
```

交互要求：

- 点击“新增目标”立即打开技能选择器；
- 选择后默认 Lv.1，可直接增减或删除；
- 无优化目标时，“计算方案”禁用并解释原因；
- 不允许存在空白目标行；
- 追踪技能默认收起，只显示总数和未达成数量；
- 自动结果应用前不得清空或调整现有成员。

### 5.5 自动配队结果预览

战斗和冒险共用同一结果预览模式：

```text
方案预览
目标达成：3 / 4
保留 8 人 · 新增 3 人 · 移除 3 人

操帆      Lv.8 → Lv.11  已达成
炮术      Lv.6 → Lv.8   差 Lv.2

成员变化
＋ 艾达、约翰、玛丽
－ 安娜、彼得、卡洛斯

[取消]                         [应用方案]
```

验收规则：

- 打开预览前后，当前舰队对象保持一致；
- 取消预览不产生任何业务状态变化；
- 应用后提供一次“撤销本次配队”；
- Solver 无解时显示原因或约束提示，不得静默清空非锁定成员；
- 所有锁定成员必须在预览中明确标记并保留。

## 6. 全局 Design System

### 6.1 视觉定位

建议正式定义为：

> 古典航海资料馆：以工具效率为主体，以海图、黄铜仪器和航海档案为轻度装饰。

游戏感主要来自配色、航海士素材、图标、标题语气和少量纹理，不来自厚重边框、复杂背景或大量装饰动画。

### 6.2 色彩 Token

| Token            |      色值 | 用途                   |
| ---------------- | --------: | ---------------------- |
| `canvas`         | `#E7DECA` | 页面底色               |
| `surface`        | `#F5EFE0` | 主卡片、表单           |

## 11. 微信小程序实施约束

- 船标签和 Chip 可以横向滚动，但必须保留边缘露出提示。

### 11.2 触控与反馈

- 重要操作热区至少 88rpx；
- 图标操作必须同时提供文字；
- 异步保存、计算、图片加载必须有进行中、成功和失败状态；
- 危险操作只在真正不可逆或影响全舰队时确认，避免弹窗泛滥。

### 11.3 性能与包体

审计阶段执行 `npm run check:miniprogram-size`，结果通过：

- 主包：2068.5KB，82 个文件；
- 三个最大文件均为 generated 数据文件；
- 首页 Hero 当前约 31.7KB；
- 冒险配队 Controller 已达到约 31.4KB。

实施要求：

- 新增 UI 素材净增长建议控制在 100KB 内；
- 不在页面响应式 `data` 中长期保存完整候选航海士集合；
- 单一目标等级、锁定状态等变更使用路径级 `setData`，不要重发完整 ViewModel；
- 技能与候选列表继续分页或切片；
- 业务计算保留在 Domain/Solver，Page Controller 只负责事件编排；
- 不新增 `wx.request`、`wx.cloud`、远程 URL 或 Node.js Runtime API；
- 不新增、删除或升级依赖，除非另行获得用户确认。

## 13. 核心验收用例

### 13.1 冒险配队

- 新增目标后一步进入技能选择，不能产生空白目标行；
- 无 Lv.1 以上目标时，计算按钮不可用；
- 无有效目标时，无论如何操作都不能改变现有成员；
- Lv.0 技能只出现在追踪区域，不进入 Solver；
- 预览取消后舰队状态完全不变；
- 应用结果后可以撤销一次；
- 所有锁定成员始终保留。

### 13.2 战斗配队

- 候选人显示技能贡献等级；
- 其他船成员显示来源船和移动语义，不使用伪禁用状态；
- “移出本次结果”“本船排除”“全舰队排除”行为互不混淆；
- 本船排除可以查看和解除；
- 自动结果应用前可以查看成员与技能差异；
- 船标签能够表达人数、目标和复核状态。

### 13.3 视觉与设备

- 320px 宽度无页面级横向溢出；
- 所有独立操作热区符合 88rpx 目标；
- 底部按钮不被安全区域遮挡；
- UI 文案全部使用繁体中文；
- 不再出现 Emoji/Unicode 充当正式功能图标；
- 页面普通正文对比度不低于 4.5:1。

### 13.4 工程门禁

- 数据、筛选和 Solver 逻辑执行 TDD；
- UI PR 提供微信 DevTools 的 320/375/430 宽度截图；
- 不修改 `archive/` 和 `miniprogram/generated/`；
- 每个 PR 提交前执行 `npm run verify`；
- Commit 前向用户展示变更文件、验证结果和拟用 Message，等待确认。

## 15. Definition of Done

一个 UI/UX Change 只有同时满足以下条件才算完成：

### 业务

- 原有功能完整保留；
- 状态含义与 Domain 一致；
- 自动配队必须经过预览确认；
- 取消、失败或无目标不能改变当前编队；
- 危险操作具有明确范围和结果反馈。

### 视觉

- 使用本报告定义的颜色、字号、间距、圆角和状态规则；
- 页面存在明确第一焦点；
- 不存在无意义容器嵌套和重复信息；
- 游戏氛围不会干扰信息阅读。

### 小程序适配

- 320/375/393/430px 宽度检查通过；
- 安全区、长文本、空状态和加载失败状态检查通过；
- 无页面级横向溢出；
- 图片资源和 `setData` 负载没有明显回退。

### 工程

- 相关单元测试、页面测试和回归测试通过；
- `npm run verify` 通过；
- 不修改生成数据和范围外文件；
- PR 中包含改造前后截图、业务验收说明和已知限制。

## 16. 最终决策摘要

后续所有 Agent 应遵循以下一句话：

> 先把配队变成安全、可理解、可预览和可撤销的工作流，再通过统一组件、紧凑布局和轻量航海视觉提高完成度；不得用装饰掩盖业务与交互问题。
