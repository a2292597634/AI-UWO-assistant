## 以後如何提出修改

- 「改舊版」：從舊維護分支建立 `codex/phase-N-具體修改`；驗證、審核及授權提交後整合回舊維護分支，只上傳舊帳號。
- 「改新版」：同樣從新維護分支出發，只上傳新帳號。新分支暫保留遷移任務名稱，便於追溯現有候選。
- 「兩邊都改」：公共修正獨立提交，再逐項 cherry-pick 到另一端；不能直接整分支互合。兩邊都要檢查與分別上傳，兩個版本號各自遞增。

公共修正的提交不要夾帶 `project.config.json` 帳號切換、單端功能開關或發布台帳。若同時涉及 master 數據，仍只手改 data/master，兩邊分別執行生成及門禁，不手改 generated。衝突按兩端功能目的解決，不用整檔覆蓋。每次在同步台帳記錄來源提交、接收提交及兩端驗證結果。

進行工作前讀對應 AGENTS，保護所有既有修改與未追蹤／必要 ignored 輸入。不要因為有固定目錄就假設當下仍在維護分支；在短期分支工作後須核對並整合回正確維護分支才能發布。

## 每次上傳前

1. 確定 old/new、版本號、具體修改及提交；先通過相關測試和完整 `npm run verify`。頁面／共享 runtime 改動按既有 HTML 驗收規範提供報告，真機與真雲另記錄。
2. 展示變更、結果及 message，按 AGENTS 取得確認後提交；未提交時只能作候選調試，不能以乾淨提交版名義上傳。
3. 在對應維護分支、乾淨工作區執行下面的只讀檢查。其 JSON 保存到該工程被忽略的 `artifacts/miniprogram-review/` 內，避免保存到根目錄反而造成 dirty。
4. 開發者工具導入對應固定入口；打開工程詳情，再核對 AppID。官方 CLI 上傳時 `--project` 明確指向檢查 JSON 中的 projectRoot，並再次執行檢查，避免檢查後又改代碼。本工具不攔截開發者工具的手動上傳按鈕，必須按此流程操作。
5. 只有明確要求上傳才執行上傳；記錄目標 AppID、版本號、完整 Git SHA、檢查／驗收報告、時間和官方成功結果。上傳開發版本、設體驗版、提交審核及正式發布是不同操作，不能相互代替。

Node 必須為 22.x。兩個目錄各自安裝鎖定依賴（`npm ci`），不要跨工作區共用 node_modules 聯結。乾淨隔離副本如缺發布測試素材可執行 `npm run assets:ci`，不覆寫原工程素材。

```powershell
# 在對應工程目錄執行。舊端：
node node_modules/tsx/dist/cli.mjs tools/release/check-target.ts --target old --project-root 'E:/AI-UWO-old'
# 新端：
node node_modules/tsx/dist/cli.mjs tools/release/check-target.ts --target new --project-root 'E:/AI-UWO-new'
```

工具要求目錄是 Git 根目錄、AppID 與維護分支匹配、Git tracked/untracked 無未提交改動、Node 22；有任何錯誤退出碼為 1。不切換分支、不改 AppID、不忽略 dirty、不上傳。檢查通過只代表帳號及 Git 版本匹配，不代表平台能力、所有素材、功能及真機通過。私有配置與環境密鑰保持 ignored，不提交、不同帳號盲目互拷；相關工具配置按工程各自設定。

## 共享雲端的特別規則

環境固定為 `cloud1-d7gxfuxfe813b4eaa`，資源方舊 AppID。前端分兩端，部署共享雲函數會同時影響兩端。

**禁止從舊維護分支整包部署雲函數。** 舊分支由 e5765d0 建立，其中函數未包含這次新端共享身份兼容。線上已完成兼容部署及首次建檔修復；用舊源碼覆蓋會破壞新端。

共享函數修改以新端遷移後的兼容實現為基礎，先核對線上差異與備份，再準備最小增量；需要同時驗證舊身份／配置仍可用、新身份隔離、新首次保存及清理，以及涉及的功能。禁止改寫舊用戶歸屬以達成共用帳號。正式部署前按既有授權與工具確認流程操作；本只讀檢查始終輸出 cloudDeploymentAllowed=false，不能作雲端部署許可。

前端回退與雲端回退獨立：舊前端可回其已驗證提交；新前端不可回到不支援共享連線的舊提交；共享雲函數不能直接回退到遷移前版本。任何雲端回退須保留兩端兼容及數據結構可用，先比較實際線上內容與備份。

舊小程序、舊環境及資源帳號需持續可用；停用或取消共享前，另做新環境／數據遷移，不能僅因舊前端停更就刪除資源。新端目前提醒／廣告、留言發布及管理員能力仍未開通，不因建立維護分支而改變。
